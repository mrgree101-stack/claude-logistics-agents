# Роль Skill

Этот Skill — рабочий помощник по обслуживанию репозитория проекта.

Он отвечает за:
- понимание и объяснение структуры репозитория;
- стартовую диагностику состояния проекта;
- безопасное внесение изменений в субагенты, Skills и скрипты;
- обновление README и CLAUDE.md;
- проверку ошибок перед публикацией;
- подготовку коммитов и публикацию на GitHub.

Он НЕ выполняет отраслевые задачи (исследование, анализ рынка, SMM) — для них существуют профильные субагенты.

# Когда использовать

Используй Skill, если пользователь просит:
- разобраться в структуре репозитория или объяснить её;
- проверить состояние проекта или найти ошибки;
- добавить или изменить субагента, Skill или скрипт;
- обновить README.md или CLAUDE.md;
- подготовить изменения к коммиту и опубликовать проект;
- запустить или проверить скрипт из папки `tasks/`.

# Карта репозитория

```text
ассистент_руководителя/
├── README.md                # описание проекта: всегда актуализировать при изменениях
├── CLAUDE.md                # инструкции главного агента: роли, правила, приоритеты
├── .claude/
│   ├── settings.local.json  # локальные настройки (в .gitignore, НЕ публиковать)
│   ├── agents/              # субагенты: research-logistics, market-auto, market-rail, market-sea, market-air
│   └── skills/              # Skills: Logistics Market Analysis, logistics-news-to-social, repo-work
├── knowledge/               # регламенты, чек-листы, справочные материалы (может быть пустой)
├── tasks/                   # материалы текущих задач, скрипты (Python)
├── отчёты/                  # итоговые отчёты (.md, .xlsx) — готовые результаты
└── reports/                 # дополнительные отчёты
```

Связь компонентов: `CLAUDE.md` определяет поведение главного агента и перечисляет субагентов; субагенты в `.claude/agents/*.md` и Skills в `.claude/skills/*/SKILL.md` объявлены YAML-фронтматтером с полями `name` и `description`. Удаление или переименование файла агента меняет доступные субагенты — изменения в этих папках требуют проверки и обновления CLAUDE.md и README.md.

# Стартовая диагностика

Перед работой с репозиторием выполнять по порядку:

1. `git status --short` и `git remote -v` — незакоммиченные изменения и адрес remote.
2. Сверить список файлов в `.claude/agents/` и `.claude/skills/` с таблицами субагентов и Skills в README.md и CLAUDE.md — обнаруженное расхождение сообщить пользователю.
3. Проверить, что изменяемые файлы читаются в UTF-8 (проект содержит кириллицу; файлы с «битой» кодировкой — сразу сообщить, не редактировать).
4. Для новых задач в `tasks/` — понять, какие исходные файлы использует скрипт, до его запуска.

Незакоммиченные чужие изменения не перетирать и не затирать принудительно; сначала показать пользователю.

# Запуск и проверка скриптов

- Синтаксическая проверка без выполнения: `python -m py_compile <script.py>` — всегда первой.
- Перед запуском скрипта, который пишет файлы (например, скрипты отчётов в `tasks/` записывают в `отчёты/`), предупредить пользователя, какой файл будет перезаписан.
- НЕ перезаписывать готовые отчёты в `отчёты/` без явного согласия пользователя; при необходимости сохранить копию с новой датой в имени.
- Учитывать среду: Windows, PowerShell 5.1 (нет операторов `&&`/`||`), пути с кириллицей. Python-скрипты проекта объявляют `# -*- coding: utf-8 -*-` — сохранять эту строку.
- Вывод работы скрипта проверять: файл создан, листы и строки на месте, стили сохранены (по правилам работы с Excel из родительского CLAUDE.md).

# Внесение изменений

Правила:

1. Субагенты и Skills — Markdown с YAML-фронтматтером; обязательные поля: `name`, `description` (одно предложение, отвечает «когда и для чего вызывать»).
2. Имена файлов субагентов — латиница kebab-case (`market-air.md`); содержимое — на русском языке, в стиле существующих файлов проекта.
3. Новый субагент или Skill добавляется одновременно в три места: файл в `.claude/`, таблицу в README.md, описание в CLAUDE.md (если меняет поведение главного агента).
4. Готовые отчёты в `отчёты/` не изменять — это результаты, а не исходники.
5. Не удалять и не переименовывать файлы субагентов без явного указания пользователя.
6. Каждое логическое изменение — отдельный коммит.

# Проверка ошибок

Чек-лист перед коммитом и публикацией:

- [ ] Все `.md`-файлы читаются как UTF-8, кириллица не искажена.
- [ ] YAML-фронтматтер корректен в каждом изменённом агенте/Skill (два поля `name` и `description`, тройные дефисы).
- [ ] `python -m py_compile` проходит для всех `.py`-файлов в `tasks/`.
- [ ] Все пути и имена файлов, упомянутые в README.md и CLAUDE.md, существуют в репозитории.
- [ ] `.gitignore` содержит `.claude/settings.local.json` и его не затронули новые `git add`.
- [ ] Нет файлов с временным/служебным содержимым (`__pycache__/`, `*.pyc`, временные копии).
- [ ] Таблицы и схемы в README.md соответствуют фактической структуре.

Найденные ошибки показывать пользователю списком с указанием файла и места; исправлять после подтверждения, кроме очевидных (опечатки, битые пути в README).

# Обновление README

README.md актуализировать, когда:

- добавлен, удалён или переименован субагент или Skill;
- изменилась структура папок;
- изменились состав или формат итоговых результатов;
- изменился MVP (список «реализовано / планируется»).

Правила:

- Сохранять структуру разделов: Название → Проблема → Пользователь → Основная функция → Формат результата → MVP → Технологии → Структура проекта → Начало работы → Принципы.
- Таблицы субагентов и Skills и схема структуры папок должны точно соответствовать файлам в репозитории.
- Не включать в README локальные пути вида `C:\Users\...` — только относительные пути.
- Не публиковать в README внутренние рабочие данные клиентов.

# Публикация

Порядок подготовки:

1. Выполнить чек-лист «Проверка ошибок».
2. `git status --short` — показать пользователю, что уйдёт в коммит.
3. Коммит: заголовок по-русски, кратко о сути; при первом упоминании изменений перечислить затронутые компоненты.
4. Push в `origin/master` (remote `https://github.com/mrgree101-stack/claude-logistics-agents.git`).
5. Не использовать `--force` без явного требования пользователя; при конфликте — сначала показать расхождение.
6. После push сообщить пользователю ссылку на репозиторий и краткое содержание изменений.

Публикация выполняется только после того, как пользователь подтвердил изменения (либо прямо попросил «опубликуй»).
